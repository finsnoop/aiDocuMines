# aiDocuMines — security and reliability audit, November 2026

Scope: the three repositories as checked out on 14 November 2026 (branch `platform-redesign` in each):
the API layer (`aiDocuMines`, Django), the sign-in service (`aiDocuMines-Backend`, Node) and the
web app (`aiDocuMines-Frontend`, Angular). Verification now includes the isolated localhost stack, using the real locked Python runtime, PostgreSQL with TLS, Redis, Elasticsearch 8, Milvus and Node 24. No remote production deployment was performed.

Status key: **Fixed** = changed in the working tree and covered by a test or a check;
**Open** = found, not changed, needs a decision or more work.

## 1. What the client complaints came from

| Complaint | Cause found | Status |
|---|---|---|
| Endpoints are not secure | Password reset returned the reset token to whoever asked; sign-up placed a stranger inside an existing organisation; an organisation admin could create a platform-wide administrator; no limit on sign-in attempts; API map (Swagger) public; debug mode on unless switched off | Fixed |
| Users see other users' data, inside and across organisations | About forty document endpoints looked a file or folder up by its id and never checked who was asking (trash, move, rename, zip, password-protect, restore, aliases, colour tags, bulk folder actions). The same pattern in redline results, clause libraries, version history, file metadata, the email outbox and the Nextcloud export | Fixed |
| The assistant exposes chats and other tenants' documents | The chat, context assistant and search code on this branch already scope every lookup to the caller (their own chats; files they can open; organisation filter in the vector search). What remained: the raw text-chunk listing was organisation-wide, and anyone with the "advanced search" permission could rebuild or delete the shared search index | Fixed |
| Containers die under memory pressure and stay down | No container had a memory cap, so the kernel killed at random (including the database). Docker restarts a container that exits but not one that is running and unhealthy; the worker health check itself loaded a second copy of the application every 30 seconds | Fixed (needs the server steps in section 4) |
| Stuck queue tasks survive restarts; people cannot sign in | (a) The web server ran one single-threaded worker, so one slow request blocked everyone, sign-in included. (b) Queuing a task while Redis was stalled hung the request forever. (c) A task whose worker was killed was put back on the queue, killed the next worker, and so on — and the queue is stored on disk, so restarts did not clear it. (d) Emails and sign-in codes waited in the same queue as multi-hour OCR jobs. (e) Jobs whose worker died stayed "Processing" forever | Fixed (needs the server steps in section 4) |

## 2. Findings

### Authentication and accounts (API layer)

| # | Severity | Finding | Status |
|---|---|---|---|
| A1 | Critical | `POST /auth/password/request-reset/` returned the reset token in its response: anyone could take over any account, including the platform superuser. It also revealed which addresses have accounts. Tokens were accepted after expiry and more than once | Fixed: token goes to the mailbox only; same answer for any address; one use, one hour; all sessions end on reset |
| A2 | Critical | Sign-up with the name of an existing organisation joined that organisation | Fixed: existing organisations are joined by invitation only |
| A3 | Critical | `POST /auth/admin/users/create/` accepted any role name: an organisation admin could create a `SuperAdmin` and read every organisation | Fixed |
| A4 | High | No limit on sign-in, sign-up, reset or refresh attempts; six-digit sign-in codes from a predictable generator with unlimited guesses | Fixed: per-address throttle, per-account pause after repeated failures, cryptographic codes |
| A5 | High | The client secret was required at sign-in and token refresh but never compared; a token could be "refreshed" forever with only the public client id | Fixed: secret verified; refresh rotates the token |
| A6 | High | Any signed-in user could delete any other user's API key; an organisation admin could read the stored client secrets of users in other organisations | Fixed |
| A7 | High | `DEBUG` defaulted to on, `SECRET_KEY` and the database password had built-in defaults | Fixed: debug off by default; the API refuses to start without a real secret key |
| A8 | Medium | Swagger/ReDoc public; no HSTS, no password rules, browsable API in production | Fixed |
| A9 | Medium | Credentials are stored and sent in clear: the sign-up email contains the password and client secret; `logs/.superuser_secrets.json` held the superuser password; client secrets are kept in a JSON file; the browser stores the client secret and token in local storage | Fixed locally: one-use set-password emails, secret JSON stores removed, public OAuth S256 PKCE, session-only browser tokens and removal of old persistent credentials |
| A10 | Medium | "Break-glass" endpoints that reset superusers or truncate every table exist in the API (off unless `ENABLE_BREAK_GLASS_ENDPOINTS=true`) | Fixed: both destructive break-glass views and routes deleted; regression tests confirm they are unavailable |
| A11 | Low | Any member of an organisation can change organisation-wide system settings | Fixed: organisation settings writes/reset require its administrator; token-derived organisation cannot be reassigned through client_id |

### Isolation between users and organisations (API layer)

| # | Severity | Finding | Status |
|---|---|---|---|
| I1 | Critical | Document operations by id with no ownership check: bulk trash, bulk move, rename (file and folder), duplicate, zip, password-protect, restore, folder trash/restore/bulk actions, aliases, colour tags. File ids are sequential numbers | Fixed: one policy (`core/access.py`) for every file and folder; unknown and foreign ids both answer 404 |
| I2 | Critical | Redline download and status by file id or run id returned other people's documents | Fixed |
| I3 | Critical | Email outbox and templates were readable and writable by any user of any organisation: it contains reset tokens and sign-in details, and could send mail as the platform | Fixed: platform administrators only |
| I4 | Critical | Nextcloud export copied any file id to the caller's Nextcloud | Fixed |
| I5 | High | Rename accepted a path (`../../…`), moving files anywhere the server can write | Fixed |
| I6 | High | Clause library and clause categories were one shared list for all organisations (read, edit, delete) | Fixed: own clauses; the organisation's admin sees the organisation's |
| I7 | High | File metadata, version status/download, automation run status and template fields by id; retention policy of any project editable by anyone | Fixed |
| I8 | High | Text chunks of every document in the organisation listed to anyone with the search permission; shared search index could be deleted or rebuilt by organisation admins | Fixed |
| I9 | Medium | Bulk folder delete and "sync user to Nextcloud" were admin-only but not limited to the admin's own organisation | Fixed |
| I10 | Medium | Clustering runs without an owner were visible to everyone; project list counted other people's files | Fixed |
| I11 | Low | Task results can be read by task id without an owner check in three places (ids are random) | Fixed: expiring owner registration and 404 for missing/foreign task IDs; anonymisation stats scoped by accessible file |

### Reliability (containers, queue)

| # | Finding | Status |
|---|---|---|
| R1 | No memory caps on any container | Fixed: caps per service, tunable in `.env` |
| R2 | Single-worker web server | Fixed: 2 processes × 8 threads by default, recycled periodically |
| R3 | Publishing a task or reading the cache could hang forever when Redis stalled | Fixed: connect/socket timeouts, bounded publish retries |
| R4 | Killed tasks were re-queued forever; no task time limits; workers never recycled | Fixed |
| R5 | One queue for everything | Fixed: a fast lane with its own worker for email, sign-in codes, chat answers and file operations |
| R6 | Work stayed "Processing" after its worker died | Fixed: swept every 15 minutes and marked Failed with a message |
| R7 | No way to clear a jammed queue | Fixed: `manage.py queue_doctor` and `./restart_containers.sh --purge-queue` |
| R8 | Unhealthy or never-started containers stayed that way | Fixed: `deploy/watchdog.sh` as a systemd timer |
| R9 | Two web requests waited on the queue with no timeout (translation status and download) | Fixed |
| R10 | First start on an empty database failed (`Group` not imported in the bootstrap); every start created another superuser application | Fixed |
| R11 | Redis: no password on a network shared with other apps, no memory limit, data not on a volume. `redis_watchdog` exists because Redis was once switched into replica mode — the usual sign of an exposed, password-less Redis being tampered with | Fixed in the compose file; **set `REDIS_PASSWORD`** |
| R12 | `restart_containers.sh` only restarted containers, so compose changes never took effect; it restarted into a broken configuration without checking | Fixed |

## 4. Putting it on the server

1. In the server's `.env` (the API refuses to start without the first two):
   - `SECRET_KEY=` a long random value — `python3 -c "import secrets; print(secrets.token_urlsafe(64))"`
   - `DEBUG=False`
   - `REDIS_PASSWORD=` a random value
   - optional capacity values — see "Capacity" in `.env.example`; make the memory caps add up to less than the server's memory.
2. Pull, then `./restart_containers.sh`. It now checks `.env` first, **builds the images** (the database now runs from a locally built TLS image; if the build fails, nothing is restarted, because the pulled code expects database TLS), applies the compose file (memory caps, health checks, the new `celery_fast` worker, Redis settings), runs migrations and restarts the application. Redis is recreated once, which empties the queue.
   **Deploy order matters.** The Node sign-in service now erases stored client secrets on
   startup (`ALTER TABLE users DROP COLUMN client_secret`), and the current production
   frontend still fetches that secret from it at sign-in. Back up the `users` table, then
   deploy the **API layer first, the frontend second and the Node service last**. Rolling the
   Node service back afterwards does not bring the secrets back.
3. Once: `sudo ./deploy/install-watchdog.sh` (restarts unhealthy or stopped containers every minute; it also tells you if the server has no swap).
4. If jobs are stuck: `./restart_containers.sh --purge-queue`.
5. Because A1–A3 were exploitable from the internet: reset the platform superuser's password, review the user list for accounts nobody recognises (especially any `SuperAdmin`), and rotate the secrets that were ever stored in clear (`logs/.superuser_secrets.json`, mail password, OpenAI key).

Behaviour changes people will notice: password-reset no longer shows the token on screen (it is emailed); new passwords need 10+ characters; signing up under an existing organisation name is refused; the email outbox and search-index tools are for platform administrators only; Swagger is off unless `ENABLE_API_DOCS=true`.

## 5. Completed follow-up and remaining release work

Completed locally:

- Integration settings credentials now use AES-GCM at rest, including conversion of legacy values and masking of audit entries (`system_settings.0003`).
- A9-A11 and I11, as recorded above. Password reset also revokes pending OAuth
  grants and refresh tokens. Sign-in email publication is bounded and asynchronous.
- Removed unused top-level view copies and legacy header-based identity calls in
  active request methods. Request identity comes from the authenticated user.
- Python 3.12 hashed CPU lock and vulnerability CI gate; Azure SDK 2 import/lazy
  initialization fixes; pypdf migration; ES 8.19.25 with client compatibility.
- PostgreSQL TLS and SCRAM for new passwords. Node verifies the database CA. The
  local role was checked; existing production roles still require password rotation.
- Queue recovery now removes only this platform's reserved messages, preserving
  other applications' shared Kombu unacked records. Watchdog/preflight regression
  tests cover failure thresholds and operator pauses.
- DOCX routing uses the filename consistently. Word documents open in the OnlyOffice
  editor as before; the mammoth preview remains the fallback when there is no editor file id.
- Persona dashboard separation and a bounded AI planning/extraction/verification
  layer with tenant/document ACLs, evidence, stale-result rejection, review controls
  and currency-separated database totals. See
  [agentic intelligence implementation](aiDocuMines/docs/AGENTIC_INTELLIGENCE.md).

- **Agent system** (`home_dash_analytics/agents/`): an orchestrator assigns documents to the
  OCR, document-intelligence and similarity agents; a resource agent watches Celery, Redis,
  PostgreSQL, the AI provider and (if `RABBITMQ_MANAGEMENT_URL` is set) RabbitMQ, and throttles
  or pauses work (healthy 3 runs per organisation, strained 1, critical 0); a cost agent turns
  tokens into US dollars from administrator-entered model prices, applies monthly budgets with
  an optional hard stop, and flags unpriced usage. Every decision is an `AgentEvent`. All AI
  calls on the platform are recorded once against the acting user (web middleware, Celery
  `task_prerun`). Settings → Agent operations shows status, spend by model and task, budget
  and prices. The rules-based extractor was removed: facts come from the model and must
  quote their evidence exactly.
- **Near-duplicate groups** are computed once per organisation and cached until the
  portfolio changes. Each person sees only the group members they may open. (Before: the
  cache was keyed by organisation and file count, so a colleague could see another person's
  filenames, and groups disappeared after an hour.)
- **Word documents no longer download by themselves.** Preview serves only inline-safe types
  (PDF, images, text) with `nosniff`/`no-store`; Word opens in OnlyOffice with the in-page
  preview as fallback; downloads happen only on an explicit Download.
- **Database connection leak fixed.** `CONN_MAX_AGE` defaults to 0 (gunicorn sets 60 through
  compose). With persistent connections under the development server, most routes failed
  with "too many clients".
- **Industry verticals and features** (`system_settings/verticals.py`): platform superusers
  switch whole verticals (Private Equity, Class Actions, Labour & Employment, IP Litigation,
  Regulatory Compliance, Immigration, Finance) or individual catalogue features on or off,
  as the platform default or per organisation at onboarding. The most specific switch wins
  (organisation + feature > organisation + vertical > platform + feature > platform +
  vertical > on), so a client can be one vertical, several, or hand-picked features. Nothing
  is deleted: the Assistant presets, Workflows, Document workspace, matter service picker,
  Insights (service analytics) and the Home department and finance sections hide what is
  off, and the API refuses it (`VerticalAccessMiddleware` for the vertical APIs, plus checks
  where catalogue services start). Changes are recorded in the admin audit log. With no
  switches set, everything stays on, so existing clients see no change at deploy.
- **Default model list** (`core/llm_providers.py`): OpenAI marks gpt-4o-mini, gpt-4.1-mini and
  gpt-5-mini as deprecated. The fallback order now starts with current models and can be set
  per deployment with `LLM_PREFERRED_MODELS`. The model chosen in Settings → Platform settings
  always comes first, so this list only matters when none is set. Moving to a newer model is a
  cost decision (gpt-5.6-terra is USD 2 / 12 per million input / output tokens against
  0.15 / 0.60 for gpt-4o-mini); prices are in Settings → Agent operations.

Deploying these: run migrations (`home_dash_analytics.0008`, `system_settings.0004`; the
restart script does this). The beat schedule adds `agent-orchestrator` (5 min),
`agent-resources` (1 min) and `agent-costs` (15 min) on the fast queue. Enter model prices
in Settings → Agent operations before relying on dollar figures. Configure each client's
verticals in Settings → Industry verticals and features.

Remaining production conditions (not represented as completed):

- **Database isolation beneath the application.** PostgreSQL RLS or a separately
  provisioned database per tenant, plus vector/storage isolation, still needs a
  deliberate migration and validation. Application RBAC tests do not establish RLS.
- **Live AI and cloud document quality.** No reachable AI provider or Azure/OnlyOffice
  test credentials are configured in the isolated local stack. Model extraction
  accuracy, OCR quality, translation quality and editing callbacks need real-service
  tests on an approved, human-labelled corpus. Unit mocks are not quality evidence.
- **Agent scale and integration coverage.** Current runs are bounded batches, not
  unlimited ingestion. Durable document fan-out, per-tenant scheduling/quotas,
  cancellation/recovery, all legacy AI usage instrumentation and live Microsoft
  connectors remain release work detailed in the architecture document.
- **Remote deployment and incident recovery.** No staging/production stack was
  supplied. Rotate exposed secrets, review privileged accounts, install watchdog,
  migrate/reindex and validate backups on the actual server before release.
- **Upstream advisory.** The exact diskcache advisory is mitigated and gated, not
  patched. Reassess the exception when an upstream fix or replacement becomes available.

## 7. Local use and deployment cautions

- UI: `http://localhost:4300`; isolated API `127.0.0.1:8030`, Node `127.0.0.1:7030`.
  `deploy/compose.audit.yml` keeps database, queue and search ports internal.
- Local credentials are in ignored `.env.audit`; do not commit or print them.
- UI serves a completed `demo` build through `scripts/serve-local.mjs`. The running
  server reads `dist/local-next` (set when it was started), not the script's default.
- Main ES 8 compose uses a **new volume**. Preserve the old ES 7 volume for rollback
  and rebuild the search index from the database after deployment; do not point ES 8
  at the old on-disk ES 7.10 data.
- Set `ENCRYPTION_SECRET_KEY`, `ELASTICSEARCH_PASSWORD` and all existing mandatory
  secrets before restarting. The new PostgreSQL container generates a private TLS
  key and shares only the public CA certificate with application containers.
- A paid OnlyOffice API subscription does not implement OneDrive, SharePoint,
  Outlook or Teams integration. Those require separate Microsoft Graph connectors,
  consent, source ACL mapping and integration tests.

Server AI configuration: the user confirmed LiteLLM, Ollama and vLLM are configured in the server environment. Local model servers are deliberately not provisioned; deployment retains environment-driven provider URLs/keys. Live-model evaluation remains a deployment check.
